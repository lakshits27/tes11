Offline library system / project 06

Pustakalaya.

A library’s daily operations, on one local machine.

Pustakalaya is a serious local-first application for library operations. It models catalog works and physical copies, members and borrowing policies, reservations, money, audit trails, and staff roles in one SQLite-backed system.

Why it exists

Problem & motivation

Library work is not just a book list. Physical copies, member tiers, due dates, reservations, fines, and staff permissions need consistent rules and an auditable record.

The spark

The project explores how to model a real operational domain carefully while still shipping something a library can run locally without a hosted service.

The approach

A layered Flask application separates domain policies, services, repositories, SQLAlchemy models, web blueprints, and Alembic migrations. SQLite runs locally with foreign keys, WAL mode, and explicit write transactions.

02

Direction

Goals and design decisions

  1. 01

    Manage catalog works and physical copy inventory across branches.

  2. 02

    Make circulation, reservations, and fines deterministic and auditable.

  3. 03

    Support real staff roles and safe first-run administration.

  4. 04

    Ship Windows builds that keep runtime data outside the application directory.

01

Local-first SQLite

Single-host operation uses foreign keys, WAL mode, busy timeouts, and explicit transactions.

02

Layered architecture

Domain entities, policies, state machines, services, repositories, and ORM models are separated.

03

Exact money handling

INR fines use integer paise storage and Decimal calculations with an auditable ledger.

04

Deterministic reservations

FIFO queues, pickup deadlines, expired holds, and idempotent reallocation are modelled explicitly.

05

Versioned schema

Alembic migrations and dataset verification scripts support repeatable setup.

03

Implemented

What the repository actually contains

These features are described in the project README or visible in its source and release material.

Catalog & inventory

ISBN validation, authors, works, physical copies, branches, conditions, and catalog search.

Members & circulation

Membership tiers, issue, return, renewal, damaged/lost workflows, and holiday-aware due dates.

Reservations

Eligibility checks, FIFO queues, pickup holds, and automatic allocation after returns.

Fines

Exact INR calculations, partial/full payments, waivers, receipts, and audit history.

Administration

Role-based access for ADMIN, LIBRARIAN, and STAFF_READONLY, plus audit and correction workflows.

Reports & imports

Operational reports, CSV exports, historical import validation, quarantine, and data-quality checks.

Reflection

Contribution, challenges & scope

My contribution

  • I authored and maintain the public Pustakalaya-LMS repository under hmmlavi.
  • The repository contains domain policies, services, SQLAlchemy repositories, Flask blueprints, Jinja templates, migrations, tests, and packaging scripts.
  • It also includes architecture, business-rule, design-decision, and data-quality documentation.

Challenges & learning

Concurrency
Atomic issue/return workflows and conditional updates prevent double checkout of one physical copy.
Correctness over shortcuts
FIFO reservations, idempotent payments, and auditable corrections need explicit state transitions.
Safe historical data
Imports classify accepted, rejected, quarantined, duplicate, and error records before they affect operations.

Documented limits

These are boundaries stated in the repository, not completed features:

  • The application is designed for reliable single-host operation; it is not a multi-node service without moving the database layer.
  • The README states that production needs an explicit secret, HTTPS/TLS, and reverse-proxy controls.
  • Screenshots in the repository were captured with synthetic demonstration data.
