FacilityFix.

Make campus issues visible from report to resolution.

FacilityFix replaces scattered facility complaints with a defined workflow. Reporters submit structured issues, coordinators manage priority and status, and both sides can follow the history of a report.

01

Why it exists

Problem & motivation

Facility issues reported through messages or verbal conversations are easy to lose. Progress, ownership, and resolution notes become unclear after the initial report.

The spark

The project turns a messy real-world process into a consistent, testable web workflow with clear roles and records.

The approach

A Flask application uses SQLite, server-rendered templates, separated services and repositories, and a Submitted → In Progress → Resolved lifecycle with a reopen path.

02

Direction

Goals and design decisions

  1. 01

    Capture facility issues in a consistent structured form.

  2. 02

    Give reporters a reliable way to follow status and history.

  3. 03

    Give coordinators a focused queue with priority and resolution tools.

  4. 04

    Demonstrate practical validation, database design, permissions, and automated tests.

01

Explicit roles

Student, Faculty, Staff, and Facility Coordinator accounts have different capabilities.

02

Defined lifecycle

Issues move from Submitted to In Progress to Resolved, with a reporter reopen path.

03

Separated layers

Database connection, issue repository, services, routes, and templates are separated.

04

Validated uploads

Optional JPEG/PNG images are limited to 2 MiB and processed server-side.

05

CLI-created accounts

Public self-registration is not included; user accounts are created through the CLI.

03

Implemented

What the repository actually contains

These features are described in the project README or visible in its source and release material.

Structured reporting

Six issue categories plus location, priority suggestion, description, and optional photo.

Role-based access

Four roles control who can submit, track, manage, and resolve issues.

Coordinator dashboard

Review the issue queue, update status and priority, and record repair notes.

Issue lifecycle

Follow Submitted, In Progress, and Resolved states with reopen support.

Persistent history

SQLite stores application data with dedicated connection, schema, and repository modules.

Automated tests

The suite covers authentication, coordinator operations, reporting, tracking, permissions, and status transitions.

Reflection

Contribution, challenges & scope

My contribution

  • I authored and maintain the public FacilityFix repository under hmmlavi.
  • The repository contains the Flask application, database layer, services, templates, static assets, screenshots, and tests.
  • It also includes installation launchers, verification notes, and requirements documentation.

Challenges & learning

Workflow clarity
Status transitions and role permissions need to be understandable to both reporters and coordinators.
Data integrity
Validation, persistence errors, and image upload restrictions are part of the test suite.
Deployment honesty
The README explicitly lists production concerns such as secret management, HTTPS, backups, and upload review.

Documented limits

These are boundaries stated in the repository, not completed features:

  • No public live demo is linked from the repository.
  • Accounts are created through the CLI; public self-registration is not part of the current setup.
  • The README says production deployment needs additional security, server, and storage review.
